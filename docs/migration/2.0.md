# Migrating from vosu 1.x to 2.0

Keep a backup of your 1.x configuration, overlays and tool data before upgrading. Stable 1.x and 2.0 prereleases use different data roots by default: prerelease builds stay isolated under `prerelease/` and only perform a read-only first-run settings import, whereas stable 2.0 release builds run the full crash-recoverable normal-root migration on first start.

## Try an alpha without moving 1.x data

All application versions with a semver prerelease suffix use `prerelease/` under their normal roots. These are the default paths; the usual XDG overrides still apply on Linux.

| What | Linux | Windows (portable, `<program>` holds `vosu.exe`) |
| --- | --- | --- |
| Config | `~/.config/vosu/prerelease/vosu.toml` | `<program>\prerelease\vosu.toml` |
| Data, including `static/` and installed packages | `~/.local/share/vosu/prerelease/` | `<program>\prerelease\` |
| Cache | `~/.cache/vosu/prerelease/` | `<program>\.cache\prerelease\` |
| Native broker | `$XDG_RUNTIME_DIR/vosu/prerelease/broker.json`; config root fallback if `XDG_RUNTIME_DIR` is unset or empty | `%LOCALAPPDATA%\vosu\prerelease\broker.json` |

At first start, if neither an alpha config nor an alpha env file takes precedence, vosu reads normal-root settings **without writing to them**. Recognized core values are layered as normal `vosu.toml` over `vosu.env` over the older legacy env file over defaults, and the five `vosu.osu` keys are imported read-only into `<config>/prerelease/plugins/settings.json`. Unreadable or malformed import input stops startup without changing the source; fix it and retry. Once alpha publishes its own config, it no longer imports normal settings. Prereleases never run the normal-root migration journal, do not copy overlays, plugins, API keys, or broker credentials, and leave `vosu.overlayhost`'s `static_folder_path` defaulted; install or copy overlays into the alpha's own `static/` instead. Explicitly setting a custom `static_folder_path` in the alpha's `vosu.overlayhost` settings can leave isolation. Do not point it at a live 1.x overlay root. Path isolation does not isolate ports: stop 1.x first or configure different overlay and dashboard ports for the alpha.

## Keep catalog sources on the matching generation

During coexistence the official [vosu-tools](https://github.com/18-lab-dev/vosu-tools), [vosulay](https://github.com/18-lab-dev/vosulay) and [vosu-overlays](https://github.com/18-lab-dev/vosu-overlays) releases carry two different catalogs once their 2.0 releases are published:

- **1.x:** `catalog.json`, a frozen, unchanged copy that still points to the exact immutable 1.x packages.
- **2.0:** `catalog-v2.json`, with new package manifests, versioned capabilities and platform assets. A repository shorthand resolves the appropriate file for the running vosu; for a literal URL use the matching filename. A tool built for 2.0 cannot be installed in 1.x by writing v1 metadata around it.

Use **Settings → Catalog sources** and the dashboard's reviewed install, update and uninstall plans in 2.0. The old immediate tool/catalog management endpoints and `vosux --sources`, `--install`, `--update` and `--uninstall` are gone. A plan shows dependencies, native runtimes, trust, required approvals and any declared install-path access. Review them before confirming. Package integrity, a read-only catalog credential and a private-network exception do not confer author trust. See [catalog coexistence](../v2/catalog-v2.md#1x-coexistence) and [native approval](../plugins/authoring.md#runtime-trust-and-native-approval).

## What the stable first-start migration transfers

On a normal (stable) root, first startup runs the offline local migration engine (`crates/vosu-core/src/migration/`) governed by the [approved migration contract](../v2/catalog-v2.md#first-start-migration-from-1x) and tracked in the crash-recoverable journal `<config>/migration-v2-journal.json`. Prerelease roots (`prerelease/`) skip this migration with zero writes.

Before any destructive write, vosu validates the destination plugin settings store and snapshots all legacy inputs (`vosu.toml > vosu.env >` legacy pre-rename env file, `catalog-sources.json`, `tools/state.json`, `tools/overlay-catalog-state.json`, and `<data>/tools/`) into `<config>/migration-v2-journal.json`. If any legacy input or destination store is malformed, startup fails closed without modifying existing files. After a crash, the next start resumes only incomplete steps from the journal snapshot; once `local_conversion_complete` is durable, later starts return immediately without rewriting anything.

The local conversion performs four ordered steps:

1. **Plugin settings import (`<config>/plugins/settings.json`):** Imports missing overrides for `vosu.osu`'s five moved keys (`CALCULATE_PP`, `POLL_RATE`, `PRECISE_DATA_POLL_RATE`, `SHOW_MP_COMMANDS`, `READ_MANIA_SCROLL_SPEED`) and `vosu.overlayhost`'s `static_folder_path` (from `STATIC_FOLDER_PATH`), each validated against that plugin's `settings.schema.json`. Existing valid per-plugin overrides in `<config>/plugins/settings.json` win per key; explicit `false`, `0`, and `""` values are preserved. Edit these settings in 2.0 under **Tools → Plugins** (`GET`/`POST /api/plugins/<id>/settings`).
2. **Core `vosu.toml` cutover:** Atomically writes canonical `vosu.toml` containing the 12 core bindings (retaining `API_V1_SUBSCRIPTION_DEBOUNCE` and any unrelated unknown keys/tables), strips the 6 moved keys above plus the 4 retired keys (`ENABLE_KEY_OVERLAY`, `ENABLE_MANIA_KEY_HIT_ERRORS`, `ENABLE_HIT_OFFSETS`, `V2_SUBSCRIPTION_DEBOUNCE`), and only then removes readable legacy `.env` files. Precise collection follows the selected API v1 fields. See [Configuration](../../README.md#configuration) for the 12 core keys and plugin settings locations.
3. **Catalog sources:** Copies 1.x `catalog-sources.json` verbatim (preserving source strings, `enabled` flags, and order) into `<config>/catalog-source-settings.json`, setting `trusted: true` only for the three exact official identities (`18-lab-dev/vosu-tools`, `18-lab-dev/vosulay`, `18-lab-dev/vosu-overlays`), `trusted: false` for every other source, and `private_network: false` for all migrated sources.
4. **Installed 1.x user tools and overlays:** Persists `enabled: false` in `<config>/tools/state.json` for every 1.x `tool.toml`-only user tool so it cannot start and is reported as `needs-2.0-update`; its package files, `<data>/tool-data/<id>/`, and `<config>/tools/settings/<id>.json` remain untouched. User overlays stay installed and enabled, and trigger a dashboard D20 notice if they call removed APIs.

The journal also records offline `pending_intents` for installed official 1.x tools and overlays. Resolution matches strictly by exact official source, same `PackageKind`, and explicit `replaces` (`0` claims → `Unmanaged`, `1` claim → `Pending`, `>1` claims → `Conflict`), with zero network calls during local conversion. If an official replacement is offline or unpublished, it remains pending; do not delete the legacy install to force it.

For official tools that split into a plugin and a web UI, the same-kind successor (for example, `map-analysis-v2`) carries the web presentation settings and tool trust/enabled state. It does **not** transfer native state across kinds. The daemon's one-time [AF.2 transfer map](../v2/ecosystem-release-matrix.md#5-settings-and-durable-data-transfer) copies legacy durable data to the named plugin's data directory and copies only mapped native settings into its settings schema; mapped secrets go only to its write-only `password` settings. `lazer-library` is plugin-only, with no replacement web UI. No plugin is granted a general legacy-directory copy facility. An AF.2 row runs after the target's first successful install but before first start: it is strictly copy-only (never moving or deleting 1.x bytes), fails closed on destination collisions instead of merging or overwriting, and resumes an interrupted copy from per-substep journal receipts. Completed rows do not run again. See the [package identity table](../v2/ecosystem-release-matrix.md#3-package-identities) for exact successors.

## Port a service or overlay package

| 1.x | 2.0 |
| --- | --- |
| `tool.toml`, `[service]`, readiness, ports, autostart and service tokens | Static `manifest.toml` with `kind = "tool"` and `[ui]`, plus a separately packaged `kind = "plugin"` for native work. There is no tool process. |
| `[api].write`, `/tools/<id>/api/*`, and host permissions | Versioned `action:` capabilities and `[[actions]]` with argument/result schemas. Declare the action in the web tool and open it through the dashboard; direct visits are read-only. For long work use [short actions around a plugin-owned operation](../v2/api-v1.md#plugin-owned-operations-af3). |
| `[api].read`, old context and file routes | Public state in a declared namespace and public session assets as API v1 resources/trees. Return private data through an authorized action and protected/sessionless files as job artifacts; never publish private data as state or a public resource. |
| Tool bridge v1, `vosu.fetch`, old host settings/context | Use `/tools/_host/v2/bridge.js`, `vosu.invoke`/`vosu.start` for actions, `vosu.settings()` for non-secret UI settings and API v1 reads for state/resources. There is no browser replacement for the old overlay-list host route; a plugin with the capability uses [`vosu.overlayhost.overlays.query`](../v2/catalog-v2.md#overlay-query-action). |
| `[cli]`, `vosux <tool>` | A plugin action with `cli = true`, exposed as `vosux <plugin-id> <action>` (or `vosu x <plugin-id> <action>`). |
| Overlay `metadata.txt` | Root `manifest.toml` with `kind = "overlay"`, shared identity fields and `resolution` if needed; declare `field:` and `resource:` capabilities. The host still reads legacy `metadata.txt` as fallback when no manifest exists; it wins neither over a manifest nor as a format for new packages. |

See the [tool protocol's exact removal list](../tools/protocol.md#deleted-404), [plugin guide](../plugins/authoring.md) and [overlay guide](../overlays/authoring.md). The old service-authoring flow is documented only in the [historical vosu 1.2.5 guide](https://github.com/18-lab-dev/vosu/blob/6566eed7b7729613d87fe1f78a01af8b9e5c7c90/docs/tools/create-a-tool.md); do not use it for 2.0 packages.

For a native replacement, use the catalog's reviewed plan and any exact
artifact approval it requests. Linux `process` plugins require kernel 5.4
or newer and a working seccomp filter, not `--setup`. A process package
requesting Linux user namespaces needs explicit approval there even from
a trusted source. Development `--plugin` approvals cannot authorize the
catalog-installed package. See [native plugin execution](../security.md#native-plugin-execution).

## Overlays and vosulay

If the dashboard shows a removed-route notice, the overlay **stays enabled**. See [Overlays that used removed APIs](../v2/migration-from-1x.md#overlays-that-used-removed-apis) for the selected-field feed, skin index and `/api/ingame` replacements, and the compatibility feeds that still work. For changed legacy payload fields, use the [1.x-to-2.0 state mapping](../v2/state-schema.md#1x-to-20-field-mapping). The notice is diagnostic, not an automatic update.

[vosulay](https://github.com/18-lab-dev/vosulay) remains supported **standalone**. For integration with vosu 2.0, install the matching native vosulay runtime through its own release channels; then install `vosulay-editor` from the official catalog. Its plan adds `vosu.vosulay` to supervise the separately installed runtime. The catalog ZIPs do not install the runtime or bundle CEF, and the daemon does not render in-game overlays itself. Standalone configuration and the attached runtime's configuration are separate.

`/api/ingame` is withdrawn, not deprecated behind a redirect: every
method gets the ordinary 404. An exact attempt on the overlay listener
can show the install or launch action in the dashboard, but does not
install anything on its own.

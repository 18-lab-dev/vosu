# Migrating from vosu 1.x to 2.0

Keep a backup of your 1.x configuration, overlays and tool data before upgrading. Stable 1.x and 2.0 prereleases use different data roots by default. A 2.0 alpha is not a test of the full stable migration: the alpha settings import already works, but the first-start package and settings migration below belongs to the stable 2.0 cutover (M8).

## Try an alpha without moving 1.x data

All application versions with a semver prerelease suffix use `prerelease/` under their normal roots. These are the default paths; the usual XDG overrides still apply on Linux.

| What | Linux | Windows (portable, `<program>` holds `vosu.exe`) |
| --- | --- | --- |
| Config | `~/.config/vosu/prerelease/vosu.toml` | `<program>\prerelease\vosu.toml` |
| Data, including `static/` and installed packages | `~/.local/share/vosu/prerelease/` | `<program>\prerelease\` |
| Cache | `~/.cache/vosu/prerelease/` | `<program>\.cache\prerelease\` |
| Native broker | `$XDG_RUNTIME_DIR/vosu/prerelease/broker.json`; config root fallback if `XDG_RUNTIME_DIR` is unset or empty | `%LOCALAPPDATA%\vosu\prerelease\broker.json` |

At first start, if neither an alpha config nor an alpha env file takes precedence, vosu reads normal-root settings **without writing to them**. Recognized values are layered as normal `vosu.toml` over `vosu.env` over the older legacy env file over defaults. Unreadable or malformed import input stops startup without changing the source; fix it and retry. Once alpha publishes its own config, it no longer imports normal settings. The import does not copy overlays, plugins, API keys, or broker credentials and drops inherited `STATIC_FOLDER_PATH`; install or copy overlays into the alpha's own `static/` instead. Explicitly setting a custom path in the alpha config can leave isolation. Do not point it at a live 1.x overlay root. Path isolation does not isolate ports: stop 1.x first or configure different overlay and dashboard ports for the alpha.

## Keep catalog sources on the matching generation

During coexistence the official [vosu-tools](https://github.com/18-lab-dev/vosu-tools), [vosulay](https://github.com/18-lab-dev/vosulay) and [vosu-overlays](https://github.com/18-lab-dev/vosu-overlays) releases carry two different catalogs once their 2.0 releases are published:

- **1.x:** `catalog.json`, a frozen, unchanged copy that still points to the exact immutable 1.x packages.
- **2.0:** `catalog-v2.json`, with new package manifests, versioned capabilities and platform assets. A repository shorthand resolves the appropriate file for the running vosu; for a literal URL use the matching filename. A tool built for 2.0 cannot be installed in 1.x by writing v1 metadata around it.

Use **Settings → Catalog sources** and the dashboard's reviewed install, update and uninstall plans in 2.0. The old immediate tool/catalog management endpoints and `vosux --sources`, `--install`, `--update` and `--uninstall` are gone. A plan shows dependencies, native runtimes, trust, required approvals and any declared install-path access. Review them before confirming. Package integrity, a read-only catalog credential and a private-network exception do not confer author trust. See [catalog coexistence](../v2/catalog-v2.md#1x-coexistence) and [native approval](../plugins/authoring.md#runtime-trust-and-native-approval).

## What the stable first-start migration transfers

This is the [approved migration contract](../v2/catalog-v2.md#first-start-migration-from-1x), not a description of what an alpha bootstrap does. Source order and enabled flags are preserved; non-official sources start untrusted. An official successor from the same source can be queued when its same-kind `replaces` names the old package. A 1.x `tool.toml`-only tool cannot run in 2.0: it is reported as `needs-2.0-update`, and its package, data and settings are not discarded. User overlays stay installed and enabled. If an official replacement is offline or unpublished, it remains pending; do not delete the legacy install to force it.

For official tools that become a plugin and a web UI, the same-kind successor (for example, `map-analysis-v2`) carries the web presentation settings and tool trust/enabled state. It does **not** transfer native state across kinds. The daemon's one-time [AF.2 transfer map](../v2/ecosystem-release-matrix.md#5-settings-and-durable-data-transfer) copies legacy durable data to the named plugin's data directory and copies only mapped native settings into its settings schema; mapped secrets go only to its write-only `password` settings. `lazer-library` is plugin-only, with no replacement web UI. No plugin is granted a general legacy-directory copy facility. An AF.2 row runs after the target's first successful install but before first start: it copies rather than moving or deleting 1.x data, refuses destination collisions instead of merging or overwriting, and resumes an interrupted copy from its journal. Completed rows do not run again. See the [package identity table](../v2/ecosystem-release-matrix.md#3-package-identities) for exact successors.

The stable configuration cutover retires `ENABLE_KEY_OVERLAY`, `ENABLE_MANIA_KEY_HIT_ERRORS`, `ENABLE_HIT_OFFSETS` and `V2_SUBSCRIPTION_DEBOUNCE`; keep `API_V1_SUBSCRIPTION_DEBOUNCE`. Precise collection follows the selected fields. In that cutover the osu!-specific settings move to `vosu.osu` and `STATIC_FOLDER_PATH` to the overlay host's `static_folder_path`; in pre-M8 builds use the [current configuration instructions](../../README.md#configuration).

## Port a service or overlay package

| 1.x | 2.0 |
| --- | --- |
| `tool.toml`, `[service]`, readiness, ports, autostart and service tokens | Static `manifest.toml` with `kind = "tool"` and `[ui]`, plus a separately packaged `kind = "plugin"` for native work. There is no tool process. |
| `[api].write`, `/tools/<id>/api/*`, and host permissions | Versioned `action:` capabilities and `[[actions]]` with argument/result schemas. Declare the action in the web tool and open it through the dashboard; direct visits are read-only. For long work use [short actions around a plugin-owned operation](../v2/api-v1.md#plugin-owned-operations-af3). |
| `[api].read`, old context and file routes | Public state in a declared namespace and public session assets as API v1 resources/trees. Return private data through an authorized action and protected/sessionless files as job artifacts; never publish private data as state or a public resource. |
| Tool bridge v1, `vosu.fetch`, old host settings/context | Use `/tools/_host/v2/bridge.js`, `vosu.invoke`/`vosu.start` for actions, `vosu.settings()` for non-secret UI settings and API v1 reads for state/resources. There is no browser replacement for the old overlay-list host route; a plugin with the capability uses [`vosu.overlayhost.overlays.query`](../v2/catalog-v2.md#overlay-query-action). |
| `[cli]`, `vosux <tool>` | A plugin action with `cli = true`, exposed as `vosux <plugin-id> <action>` (or `vosu x <plugin-id> <action>`). |
| Overlay `metadata.txt` | Root `manifest.toml` with `kind = "overlay"`, shared identity fields and `resolution` if needed; declare `field:` and `resource:` capabilities. The host still reads legacy `metadata.txt` as fallback when no manifest exists; it wins neither over a manifest nor as a format for new packages. |

See the [tool protocol's exact removal list](../tools/protocol.md#deleted-404), [plugin guide](../plugins/authoring.md) and [overlay guide](../overlays/authoring.md). The old service-authoring flow is documented only in the [historical vosu 1.2.5 guide](https://github.com/18-lab-dev/vosu/blob/6566eed7b7729613d87fe1f78a01af8b9e5c7c90/docs/tools/create-a-tool.md); do not use it for 2.0 packages.

## Overlays and vosulay

If the dashboard shows a removed-route notice, the overlay **stays enabled**. See [Overlays that used removed APIs](../v2/migration-from-1x.md#overlays-that-used-removed-apis) for the selected-field feed, skin index and `/api/ingame` replacements, and the compatibility feeds that still work. For changed legacy payload fields, use the [1.x-to-2.0 state mapping](../v2/state-schema.md#1x-to-20-field-mapping). The notice is diagnostic, not an automatic update.

[vosulay](https://github.com/18-lab-dev/vosulay) remains supported **standalone**. For integration with vosu 2.0, install the matching native vosulay runtime through its own release channels; then install `vosulay-editor` from the official catalog. Its plan adds `vosu.vosulay` to supervise the separately installed runtime. The catalog ZIPs do not install the runtime or bundle CEF, and the daemon does not render in-game overlays itself. Standalone configuration and the attached runtime's configuration are separate.
